# Minimal credential model

Public documentation checked on 2026-09-04. This describes current credentials
and proposed user-facing changes, not a completed personal-storage integration.

## Current installation

- Deployment uses an operator's local HF authentication to inspect the existing
  resources and update the control Space. It is not copied into remote workers.
  Installer verification/activation use a separate temporary browser session with
  the existing Space OAuth login, not another manually created token. The planned
  operator signs in interactively; cookies are neither exported nor persisted by
  the installer. Explicitly configured approved application bearers remain an
  optional automation transport, never a fallback to the management credential.
- The control Space retains `HF_TOKEN`: a fine-grained credential with read/write
  access to the canonical artifact Bucket and Job management in the configured
  namespace. The installer no longer requires Endpoint-management permission for
  a Jobs-only installation. Endpoint operations still require their own provider
  permissions; existing Endpoint credentials must not be narrowed before a
  consumer audit and cleanup canary.
- `HF_INFERENCE_TOKEN` is separate and inference-only. Only reviewed execution
  workers requiring inference receive it. Setup and preparation do not.
- Enabling `hf_oauth: true` lets Spaces supply the OAuth client ID and secret.
  These are platform-managed, not additional operator-created access tokens.
- Sessions, CSRF tokens, and scoped worker capabilities are generated by the
  application. Users do not provision them.

Browser users sign in with HF without supplying an access token. With a
configured ACL, users outside the operator/reader lists get only limited
submitter access. Login does not delegate private
Bucket access or make execution user-funded. Saved recipes currently occupy
account-scoped prefixes in the canonical Bucket; administrators of that Bucket
can inspect them.

## Personal-Bucket OAuth: what is verified

The [Spaces OAuth guide](https://huggingface.co/docs/hub/spaces-oauth) explicitly
mentions combining login with personal Storage Buckets. Its published scopes,
and the [general OAuth guide](https://huggingface.co/docs/hub/oauth), list
`read-repos`, `write-repos`, `manage-repos`, and `contribute-repos`, but do not
specify a Bucket-specific scope or a consent restriction to one selected existing
Bucket. The [Bucket security guide](https://huggingface.co/docs/hub/storage-buckets-security)
documents scoped user access tokens, not an exact OAuth-to-Bucket permission map.

Therefore personal-Bucket OAuth is documented as a use case, but the minimum
working scope and per-Bucket restriction are not verified. Do not assume that
repository scopes cover every Bucket operation, or request broad repository
write access silently. `contribute-repos` concerns resources created by the app;
it does not document access to an arbitrary existing personal Bucket.

Spaces documents an eight-hour default token duration, configurable up to
30 days. The live [OpenID metadata](https://huggingface.co/.well-known/openid-configuration)
advertises `refresh_token` grants. That does not establish whether this Space's
particular flow receives refresh tokens or their rotation/revocation behavior.
The no-refresh statement in the general OAuth guide concerns its enterprise
organization token-exchange section, not necessarily browser authorization-code
login. Current application login retains identity/session state, not delegated
OAuth tokens for Bucket access.

Before implementing delegation, confirm the missing permission and renewal
semantics with HF or a specifically approved disposable-data canary in an
existing user Bucket. No Bucket creation, credential transfer, or live write was
performed for this documentation review.

## Hosted leaderboard submission flow

Users do not need write access to the admin Bucket, membership in the
admin organization, or a manually pasted token merely to submit results.

1. Sign in with HF.
2. Choose an eligible hosted result owned by the signed-in identity.
3. Preview the exact public metadata, then explicitly consent and submit.
4. The control service validates the submission and stores a pending record in
   the canonical Bucket using its own credential.
5. An administrator reviews and separately publishes an immutable leaderboard
   entry. Personal-Bucket access is not a prerequisite for this flow.

Hosted results reference existing evidence without copying it. External uploads
are deferred pending a supported Harbor validation boundary. Any future uploads
must remain explicitly externally supplied: a valid `result.json` or
checksum alone does not prove trusted execution. Validate the Harbor lock,
configuration, result and available evidence through the existing result
boundary; scan for secrets and private identifiers; retain provenance and avoid
claiming equivalence with verified hosted results without sufficient evidence.
Submission does not authorize public disclosure of operator-specific data.

Use the existing shared Bucket and control authority, not a second publication
service. Ordinary submitters must not inherit operator permissions to launch
admin-funded Jobs, modify presets, or publish directly. See
[hosted submissions](leaderboard-submissions.md) for the implemented boundary.
